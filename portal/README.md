# Portal 请求层

这一层负责请求分流和调用顺序，不实现存储算法、训练进程或 GPU 选卡。

| 文件 | 职责 |
| --- | --- |
| `operation-routes.mjs` | 操作对应的处理路径，以及哪些响应只返回本次回执 |
| `dataset-requests.mjs` | `DatasetRequests`：数据查询、标签、删除和容量统计的请求协调；统一目录并发名额收尾 |
| `request-identity.mjs` | 无副作用的身份比较和请求参数复制 |
| `../portal-service.mjs` | 唯一状态所有者、服务生命周期、账号事务和串行写入队列；`invoke` 只分流，`invokeSerialized` 处理队列内操作 |

## 约定

- 加操作时先明确它是独立查询、长连接，还是必须串行的写入；不要随意绕开账号与调度队列。
- 业务细节放在对应模块，不往 `invoke` 增加新的长分支。数据读写实现仍在已有的数据模块，节点通信仍经现有执行边界。
- 参数在请求入口核对并复制一次。权限在进入操作和异步结果返回时核对；两个检查之间没有异步工作时，不重复检查同一件事。
- 使用 `catalogSlot` 统一占用和释放并发名额；异常也必须释放。它不处理上传字节、任务调度或数据库事务。
- 请求分流不授予权限。领域模块仍负责具体数据／机器权限；未知操作仍交给原串行路径验证，不猜成安全查询。
- 历史名称 `datasetRead` 指独立的数据处理通道，并非“只读许可”：显式缓存准备、释放和取消也在此通道，仍由各自领域模块检查写入权限；本轮没有把它们变成只读或绕过授权。
- 不新增通用工作流框架、事件总线或动态插件机制。这一轮不改数据库格式、RPC 名称、节点协议或外部命令。

这是渐进拆分的第一步。上传查询、终端和云请求仍沿用原处理路径；后续按独立调用链迁移，不为目录好看一次移动所有文件。真实灰度入口当前仍转发现役控制端，这些后端重构不能被描述为已经在生产接管状态。
