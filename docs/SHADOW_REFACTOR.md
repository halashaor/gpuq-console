# 影子版本优化计划

实现标准已升级为[完整重构架构](ARCHITECTURE_V2.md)。此前的 `DatasetRequests(portal)` 拆分仍依赖整个旧服务，只保留为实验和回归依据，不再按该结构扩展。以下灰度运行、单写者和回退约束继续有效；具体模块设计以 V2 标准为准。

状态：真实资源灰度入口正在实施。稳定版保持默认；灰度网页／CLI 经显式选择访问同一个状态所有者。部署回执另记，本文不作为已上线证明。

## 目标和基线

保留现有网页、CLI、调度、个人容器、数据和恢复功能，整理实现，不另造一套产品或改用户工作流。

基线为已公开的生产快照 `759a53f`，整合共享原目录读取 #272 和两项已定向验证的界面／错误码修复，当前分支从 `2a4315d` 创建。这不是已验收发布版本。原工作区内尚未提交的测试修正保留原地，逐项验证后再移入，不自动捎带发布。

已确认的问题是生产、公开主线、节点固定运行器和测试契约发生分叉；部分旧测试仍期待已经停用的中转接口。不能把所有失败都当作产品故障，也不能一律归为旧测试而跳过。文件长短本身不是重构依据。

## 整理成五个明确边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| 身份与权限 | 当前用户、角色、机器和数据授权 | 数据搬运、GPU 分配 |
| 任务与调度 | 任务状态、优先级、选卡、抢占、租约 | 容器实现、网页展示 |
| 项目与执行 | 开发会话、代码版本、容器和训练进程 | 决定调度优先级 |
| 数据与传输 | 原目录只读访问、固定版本、缓存、上传续传、结果下载 | 把入库设成所有读取的前置条件 |
| 接口与界面 | 网页和 CLI 共用的操作契约、状态和错误展示 | 各自再实现一遍业务规则 |

先在同一项目内拆清责任，不引入微服务、消息队列或通用工作流框架。每次只迁一个调用链，原行为仍可追溯。

## 哪些保护保留，哪些合并

- 保留账号隔离、GPU 唯一分配、同一操作不重复写入、原 UUID 恢复、数据完整性和不可逆操作确认。
- 合并散落的重复解析、同层多次鉴权、同一目录反复扫描，以及用途重叠的兼容分支和启动包装器。跨越身份或异步执行边界的复查不能机械删除。
- 每项保护注明它防止的具体故障、所属边界和回归用例；没有证据的限制先核查，再删，不为让测试变绿而放宽断言。
- 缺失的只读统计可显示未确认，不因此阻断无关功能；GPU 所有权、写入结果或授权未确认仍不得猜成成功。异常隔离到受影响的任务、卡或节点。

## 真实灰度入口

1. 同一 VPS 上的独立、限额、无生产卷挂载容器，仅接管 `/__preview__/`；普通入口仍是稳定版。配置显式测试用户 ID 名单，每次请求向现役控制端核验身份。
2. 首阶段是灰度网页和 CLI，不宣称已完成后端重构。灰度使用真实账号、项目、上传和训练，通过现役 API 执行；不建立第二份生产数据库或第二个调度器。写请求只转发一次，失败不会自动改走稳定路径重新提交。
3. 灰度容器不挂生产数据库、执行桥、Docker socket 或 SSH 私钥，不运行独立派发、通知、清理和恢复 worker。任务仍由现役 GPUQ 统一分配，稳定与灰度共享任务身份和读取结果。
4. 在稳定网页登录后，获授权用户打开 `/__preview__/`；页面标记“灰度版 · 真实资源”。灰度网页不提供第二套登录账户，会话失效须回稳定入口登录。
5. 独立安装的 `gpuctl-preview` 不替换原 `gpuctl`。执行 `gpuctl-preview preview on` 后，该客户端调用灰度入口；`preview off` 在灰度停机时也能退出；`preview status` 查看当前选择。退出不取消已有任务。尚未支持该命令的旧 CLI 不会被描述为自动升级成功。
6. 后续将后端业务拆成可按灰度渠道选择的实现，但共用唯一状态写入者。新节点运行器按明确灰度任务选择；不能把当前 API 转发当作已经验证了新调度器。

## 分步交付和验收

已完成的拆分实验：请求处理路径集中在 `portal/operation-routes.mjs`，数据请求协调移入 `DatasetRequests`，原串行写入顺序保持。它尚未消除对整个 `PortalService` 的依赖，不作为完整重构的完成标准。这批实验代码没有切换生产状态所有者。

1. **建立可信基线**：列出现役功能与接口、生产模块和节点入口；将失败逐项分为产品 bug、测试契约过期、环境或不确定项。记录修复前后证据，不把当前失败全删掉。
2. **先整理数据读取链**：读取、发布、缓存准备互不隐式触发；验证已有目录直接只读、多个任务共用原文件、缓存不足不妨碍原目录读取。
3. **整理执行和状态链**：统一网页／CLI 操作契约与错误，收敛同功能运行器及桥接层；保留原任务和发布版本身份。
4. **整理调度链**：先把选卡决策做成无副作用逻辑，再接执行器；覆盖固定／任意选卡、共享、优先级、抢占保存和恢复、合法弹性卡数、局部冲突隔离。
5. **完整验收**：单元、真实临时节点、浏览器和构建回归；增加并发、断连、重启、丢回执、取消、磁盘不足等场景。所有保留功能要有覆盖；耗时和资源峰值与基线对比，目标在测量基线后确定。

每一步留下独立提交和兼容说明；影子分支失败不得改生产兜底。生产期间新增修复也须定期整合并重新验证，不能长期分叉后一次强行覆盖。

## 最后切换，不同时运行两套写入者

- 切换前冻结确切源码、镜像、节点运行器和配置版本，备份状态，验证兼容性和回退演练；向用户报告范围与短暂影响。
- 短暂关闭新任务派发，等待门户在途写入完成；已有训练继续运行。新版本必须能识别、查询和控制旧任务、租约和上传回执。
- 复用并验证现役门户交接协议：候选先转发而不打开生产数据库，进入 hold 后排空请求，停止旧数据库所有者及其后台派发／清理 worker，再激活新所有者。切换清单还须包含独立 systemd worker；旧服务的自动重启必须不能绕过所有权检查。缺少该证明时不得切换，不能只换 HTTP 路由。
- 旧控制端释放写入权后，新端才接管。生产数据库保留为唯一真相，绝不用影子数据库覆盖它，也不重放影子请求。
- 灰度网页和 CLI 已可转发真实操作，但仍由稳定控制端作为唯一写入者；新调度逻辑先只做决策对比。正式切换仍不能按入口把状态写请求分给两个独立所有者。节点运行器可先在专用测试节点灰度：仍由唯一现役控制端派发到显式指定的新运行器，旧任务保留旧路径。核对一个真实训练生命周期后再扩大；发现重复派发、旧任务失联或读取损坏即停止扩面。
- 回退切回旧程序和配置，不用旧数据库快照抹掉新任务。若必须做不兼容迁移或中断现有训练，另行确认，不把它藏在“影子替换”里。

用户已授权并行优化和后续替换，以及节点配套更新；这不授权删除数据、迁盘或停止现有训练。当前优先完成隔离底座和第一条数据读取链，未宣称整个重构已经完成。
