# 多机自动选机

固定服务器的原命令继续有效。自动模式必须主动指定候选范围，一项训练仍在一台服务器上跑；不会跨机器拼卡或启动跨机 DDP。

```sh
gpuctl run auto --hosts all -g 2 --project vision --release 完整64位版本 -- python train.py
gpuctl run auto --hosts gpu-1,gpu-2 -g 2 --project vision \
  --target-release gpu-1=完整64位版本A --target-release gpu-2=完整64位版本B \
  -- python train.py
```

`all` 展开为当前账号已授权的服务器，也可写逗号分隔的子集。使用项目时必须显式 `--project`，不沿用单机记住的项目；未指定时走各候选服务器的原个人工作区，需自己先准备相同代码和依赖。

项目名在各候选节点相同。`--release` 是默认固定版本，`--target-release SERVER=HASH` 可覆盖某节点自己的 READY release；没有默认版本时须为每个候选节点给出完整映射。不会自动读取 latest，也不会自动同步代码、数据或环境。

`--data 名称@版本`、训练命令和参数保持完全一致，所有候选节点须有该账号可读、名称和版本完全相同的 READY 数据。手动同步后名称不同的副本不能自动替换；使用正确的引用重提任务，或只选择拥有该引用的节点。

网页打开工作台的“提交训练 → 服务器调度范围”，选择自动模式，再勾选服务器。项目与默认固定版本取自工作台当前项目，文本框可写每节点的 `SERVER=HASH`。刷新状态不会重置候选选择和版本草稿。

## 排队、优先级与取消

`gpuctl jobs` 或网页任务表显示 `WAITING_POOL`、候选范围和原因。按 P0–P4 排序，同等级按提交顺序。高等级等待任务仅阻止其已准备就绪的可运行节点，不会因另一节点缺代码或数据堵住所有服务器。

优先使用所有候选中的空闲卡，再考虑原 GPUQ 规则允许的低优先级自愿让位任务。普通排队也可使用明确愿意被抢占的任务；模式 1/2 及训练适配要求沿用既有约定。共享任务需要明确观察并选择机器与显卡，使用固定服务器模式。

```sh
gpuctl watch 任务UUID
gpuctl cancel 任务UUID
```

尚未选机时取消直接完成。选机后只向原节点确认取消；接纳或停止结果不明确时显示 UNKNOWN、保留额度，并核对原节点与原提交键。只有节点原子确认拒绝接纳，才可重新选机。已启动任务不会自动迁移到另一台服务器。

## 弹性卡数与额度

自动选机可沿用 `--min-cards / --global-batch / --micro-batch / --auto-expand`。仍只用整除 global batch 的合法卡数；一台节点内按可用最多卡数启动。

全局额度按原申请最大卡数预留，本机最大卡数固定为原请求、节点物理卡数和该节点绝对个人额度的最小值。其他自己的任务占用额度时等待释放，不因当时只剩一张空卡永久缩成一张。

若本机范围只有一种合法卡数，本任务实际不自动扩卡，任务表明确显示本机上限和全局预留。例如原请求最大 8、最低 2，某节点额度 2：本机上限 2，自动扩卡关闭，全局仍预留 8。选定后提高额度不会修改已固定的训练合同；需要更高上限时取消并按新范围提交。

## 上线与回退

先部署经过验证的 GPUQ 原子接纳/取消协议与节点桥，确认新鲜状态同时公布 `fleet-admission-v2` 和 `console-fleet-v1`，再发布门户和已打包客户端。未知、离线或旧协议节点不会被当作空闲节点。

门户状态增加私有 request/routing 和可读候选范围，固定服务器旧提交、摘要、job spec 保持兼容。回退前停止新增自动任务，并让已经选机或 UNKNOWN 的任务继续由理解其接纳协议的版本核对；不能删除路由记录或清空额度后重新提交。已有历史自动记录不会仅因字段相似就触发重新派发。
